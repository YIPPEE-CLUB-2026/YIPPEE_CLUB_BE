# YIPPEE CLUB 백엔드 (Spring)

Django 서버(`YIPPEE_CLUB_BE`, main `c163a6c`)를 API 명세 v1.5 그대로 옮기고, 주문·결제를 더한 스프링 부트 서버입니다.
Java 17, Spring Boot 4.1, MySQL 8, Flyway.

**API의 요청·응답 형식은 [docs/API_SPEC.md](docs/API_SPEC.md)에 있습니다**(프론트엔드용, 기존 v1.5 명세의 번호 병기).

**Swagger 화면**: `SWAGGER_ENABLED=true`인 서버의 `/swagger-ui/index.html`. 기본은 꺼져 있고(관리자 API까지 모든 주소가 보이므로
운영 서버에서는 켜지 않습니다), 개발 서버에는 켜 두었습니다. 로그인(`POST /api/v1/auth/login`) 응답의 `access_token`을 **Authorize**에
붙여 넣으면 자물쇠가 붙은 API를 부를 수 있습니다. Access 토큰은 5분(`JWT_ACCESS_TTL_SECONDS`) 뒤 만료되어 다시 넣어야 합니다.
요청 본문의 필드는 화면에 나오지 않으므로(JSON을 직접 적음) 명세서를 함께 봅니다. 활동지 등록(`POST /admin/activities`)만 입력 칸이 있습니다.

## 들어 있는 것

| 묶음 | API |
|---|---|
| 인증·프로필 | 이메일 인증번호, 가입, 로그인, 소셜 로그인(카카오·네이버·구글), 토큰 갱신, 로그아웃, 프로필, 비밀번호 변경·재설정 (13개) |
| 아이 | 등록·목록·상세·수정·삭제, 선택한 아이 (6개) |
| 활동지 | 카테고리, 목록·검색, 상세, 표지·PDF 파일 (5개) |
| 찜·장바구니 | 추가·목록·삭제 (6개) |
| 주문·결제 | 예상 금액, 주문(영구 소장/7일 이용권), 결제 승인, 웹훅, 내역·상세·영수증, 결제 전 취소·결제 후 환불 요청, 구매한 활동지, 다운로드 링크 (10개) |
| 관리자 | 카테고리 등록, 활동지 등록·수정·파일 교체, 주문 목록·상세·재조회·환불, 환불 요청 목록·수락·거절, 사용자 조회·정지 (13개, 명세 밖) |

관리자 API(`/api/v1/admin/*`, `ADMIN_EMAILS`의 계정만):

| 주소 | 하는 일 |
|---|---|
| `POST categories` | 카테고리 등록 |
| `POST activities` (폼 업로드) | 활동지 등록: 제목, 설명, 개월 수, 난이도, 시간, 가격(`price`), 7일 이용권 가격(`rental_price`, 선택), 공개 여부, 카테고리, 표지·PDF |
| `PATCH activities/{id}` | 가격·공개 여부 등 수정. `rental_price`는 숫자면 설정, `null`이면 7일 이용권을 없앰 |
| `POST activities/{id}/files` (폼 업로드) | 표지나 PDF 교체 |
| `GET orders?status=review` | 사람이 봐야 하는 주문 목록(상태별 조회) |
| `GET orders/{id}` | 주문 한 건과 분쟁 때 필요한 기록: 환불 고지에 동의한 시각, 결제 시각, PDF별 다운로드 횟수와 처음·마지막 시각 |
| `POST orders/{id}/reconcile` | 결제사에 그 주문을 다시 물어봄(웹훅을 놓쳤을 때) |
| `POST orders/{id}/refund` | 전액 환불. 결제사가 환불을 확인해 준 뒤에만 권한을 회수 |
| `GET orders/refund-requests?status=requested` | 구매자의 환불 요청 목록. 사유, 결제·동의 시각, 다운로드 기록이 함께 나옴 |
| `POST orders/refund-requests/{id}/approve` | 수락: 결제사에서 전액 환불. 결제사가 환불을 확인해 준 때에 요청이 `approved`가 됨 |
| `POST orders/refund-requests/{id}/reject` `{note}` | 거절. `note`는 구매자가 주문 상세에서 읽는 답 |
| `GET users?email=` · `PATCH users/{id}` | 사용자 조회, 계정 정지·복구(정지하면 토큰이 바로 끊김) |

## 실행

```bash
./gradlew test          # H2(MySQL 모드)로 전체 테스트
./gradlew bootRun       # .env.example의 환경변수가 필요합니다
```

환경변수는 [.env.example](.env.example)에 이름과 뜻이 있습니다. 이름은 Django 서버의 `.env`와 같고, 새로 생긴 것은
`FORWARD_HEADERS_STRATEGY`, `TOSS_SECRET_KEY`, `ADMIN_EMAILS`, `DB_POOL_SIZE`입니다.

같은 테스트를 실제 MySQL로 돌리려면 `TEST_DATABASE_URL`, `TEST_DATABASE_USER`, `TEST_DATABASE_PASSWORD`를 주고
`./gradlew test`를 실행합니다. [CI](.github/workflows/ci.yml)가 H2와 MySQL 두 번을 돌립니다.

## 개발 서버 (2026-11-24부터, AWS 시드니)

개발과 PG 심사 준비용입니다. 구매자가 한국에 있어 요청마다 약 0.2초가 더 걸리므로, 정식 오픈 전에 서울 리전으로 옮깁니다.

같은 날 저녁에 다른 AWS 프로젝트로 옮겼고, 처음 서버는 지웠습니다. 같은 설정 파일로 새로 세운 서버이고(옮길 데이터는 없었습니다), 로그인 없이 되는 요청
34가지의 응답이 처음 서버와 같은 것을 확인했습니다(한 건은 JSON 키 순서만 달랐습니다). MySQL에서의 전체 테스트는 처음 서버에서 돌린 것이고, 새 서버의 MySQL은 같은 판(8.0.46)입니다.

- **구성**: `t3.micro`(1GB) 한 대에 앱과 MySQL 8.0을 함께 둡니다. Ubuntu 24.04, 디스크 20GB(암호화), 고정 주소.
  서버 설정은 [deploy/setup-server.sh](deploy/setup-server.sh) 하나이고, 새 서버의 첫 부팅 때(EC2 사용자 데이터) 한 번 실행됩니다.
  서울로 옮길 때도 같은 파일을 씁니다.
- **열려 있는 곳**: SSH(22)는 **개발자 한 사람의 인터넷 주소에서만** 열려 있습니다. API(8080)는 2026-11-25부터
  **모든 주소에 열려 있습니다**(Swagger를 팀이 볼 수 있게 소유자가 직접 연 것). 암호화 없는 HTTP라서 주소를
  `http://`로 적어야 하고(`https://`로는 안 열림), 비밀번호와 토큰이 평문으로 지나갑니다. HTTPS 페이지로 배포된
  프론트는 브라우저가 막아서 이 주소를 부를 수 없습니다.
- **도메인과 HTTPS (2026-11-25 준비)**: 서비스 도메인은 `www.yippeclub.com`(프론트), API는 `https://api.yippeclub.com`입니다.
  서버에 Caddy를 설치해 443으로 받은 요청을 앱(8080)으로 넘기게 했고([deploy/Caddyfile](deploy/Caddyfile)), 80·443을 열었습니다.
  인증서는 Caddy가 스스로 받고 갱신합니다. **DNS에 `api` A 레코드(서버의 고정 주소)가 들어가야 인증서가 발급되고 그때부터
  열립니다.** 그 전까지 `https://api.yippeclub.com`은 동작하지 않습니다. 함께 바꾼 서버 설정: 허용 origin에
  `https://www.yippeclub.com`과 `https://yippeclub.com` 추가(로컬 주소는 유지), 비밀번호 재설정 페이지를
  `https://www.yippeclub.com/password/reset`으로 지정(프론트가 이 경로에 페이지를 만들어야 함), `FORWARD_HEADERS_STRATEGY=native`.
  프록시 헤더는 서버 안의 프록시가 보낸 것만 믿고, 8080으로 직접 들어온 요청이 보낸 것은 무시되는 것을 확인했습니다.
- **비밀값**: 서버의 `/etc/yippee/env`(root만 읽음)에 있습니다. `SECRET_KEY`와 DB 비밀번호는 서버가 스스로 만들었고 어디에도
  출력되지 않았습니다. `CORS_ALLOWED_ORIGINS`(로컬 프론트 `localhost:3000`)와 메일 서버 주소(Gmail)는 들어 있습니다. `TOSS_SECRET_KEY`, 메일 계정(`EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`), `PASSWORD_RESET_FRONTEND_URL`, `ADMIN_EMAILS`, `REQUIRED_AGREEMENTS`는 비어 있어 사람이 채워야 합니다.
  지금 개발 서버에는 메일 계정(2026-11-25 첫 가입에서 인증 메일이 실제로 도착), 관리자 이메일, 토스 테스트 키가 들어 있습니다. 토스는 이
  서버에서 온 호출을 받아 줍니다(없는 결제 조회에 404 `NOT_FOUND_PAYMENT`). 토스 개발자센터의 "API 키 접근 정책"에 서버의 고정 주소가
  허용돼 있어야 하므로, **서버 주소가 바뀌면 그 정책도 고쳐야 합니다**(안 고치면 403 `API_KEY_ACCESS_DENIED`).
  채우기 전에는 가입(인증 메일), 비밀번호 재설정 메일(500), 유료 주문이 되지 않습니다. 고친 뒤 `sudo systemctl restart yippee`.
- **새 버전 올리기**: `./gradlew bootJar`로 만든 jar를 서버로 복사해
  `sudo install -o yippee -g yippee -m 640 app.jar /opt/yippee/app.jar && sudo systemctl restart yippee`.
  PDF와 표지는 `/data/yippee-files`에 있어 jar를 바꿔도 남습니다. 백업은 아직 걸어 두지 않았습니다.
- **MySQL에서 테스트 다시 돌리기**: 소스를 서버에 올리고 `/etc/yippee/test.env`의 세 값을 환경변수로 준 뒤 `./gradlew test`.
  테스트는 전용 DB(`yippee_club_test`)와 전용 계정을 써서 앱의 DB를 건드리지 않습니다. 1GB 서버라 테스트 JVM 힙을 지정해야 합니다(600MB로 돌렸습니다).
- **스키마 변경**: `V1__init.sql`과 `V2__social_accounts_and_download_origin.sql`(2026-11-25)은 이 서버의 DB에 적용됐습니다.
  **이제 두 파일은 주석 한 줄도 고치면 안 됩니다**(Flyway가 내용이 바뀐 것을 보고 시작을 거부합니다). 스키마를 바꿀 때는
  `V3__…sql`을 새로 추가합니다.
- **CPU**: 초과 사용 과금이 없도록 `standard` 모드입니다. 배포 직후처럼 CPU를 오래 쓰면 느려질 수 있습니다.

## EC2에 올릴 때

- **로드밸런서 뒤**: `FORWARD_HEADERS_STRATEGY=native`. 이 값이 없으면 접속 제한이 모든 사용자 공용이 되고,
  응답의 파일 주소가 `http://`로 나갑니다.
- **상태 점검**: 로드밸런서는 `GET /api/v1/health/ready`를 봅니다(DB까지 확인). `/api/v1/health/`는 프로세스만 봅니다.
- **DB**: RDS MySQL 8. 스키마는 서버가 뜰 때 Flyway가 만듭니다. `DB_POOL_SIZE × 서버 수`가 RDS의
  `max_connections`보다 작아야 합니다.
- **파일**: 저장 위치는 EC2 인프라를 구성할 때 정합니다(팀 결정). 코드가 요구하는 것은 세 가지뿐입니다.
  `ACTIVITY_PRIVATE_ROOT`가 ① 재배포 뒤에도 남는 디스크이고 ② 백업되며 ③ 앱 서버가 두 대 이상이면 모든 서버가
  같은 폴더를 보는 것(공유 디스크, 또는 그때 S3·R2로 옮김. 파일을 다루는 코드는 `Activities.java` 한 곳).
- **Docker로 띄울 때는 파일 폴더를 반드시 밖에 둡니다.** 컨테이너 안의 `/app/private_uploads`는 새 컨테이너가
  뜨면 비어 있습니다. 호스트 폴더를 붙이세요: `-v /data/yippee-files:/app/private_uploads`.
  그 폴더의 주인은 uid `10001`이어야 하고(`chown 10001 /data/yippee-files`), EBS 스냅샷 같은 백업을 걸어 둡니다.
  이걸 빠뜨리면 재배포 때 PDF가 전부 사라지는데 DB에는 "구매함"으로 남습니다.
- **메일**: SMTP로 보냅니다. Resend 설정은 `.env.example`에 있습니다. 발신 주소는 Resend에서 인증한 도메인이어야 합니다.
- **로그**: 요청마다 한 줄(`access` 로거: 메서드, 경로, 상태, 걸린 시간, 요청 ID)이 표준 출력으로 나갑니다.
  응답의 `X-Request-Id`와 오류 본문의 `request_id`가 같은 값입니다. 바로 봐야 하는 경보는 아래 "사람이 직접 해야 하는 일"에 있습니다.
- **필수 약관**: `REQUIRED_AGREEMENTS=terms,privacy`처럼 넣으면 가입 때 그 키가 `true`여야 합니다. 비워 두면 검사하지 않습니다.
- **비밀값**: `.env` 파일이 아니라 Parameter Store 같은 저장소에서 주입합니다.
- **종료**: 배포로 프로세스가 내려갈 때 처리 중인 요청을 20초까지 기다립니다.
- **관리자**: `ADMIN_EMAILS`에 적힌 이메일로 가입한 계정만 `/api/v1/admin/*`을 쓸 수 있습니다.
- **결제 웹훅**: 토스페이먼츠 개발자센터에 `https://<도메인>/api/v1/payments/webhook`을 등록합니다.

## Django 서버와 달라진 점 (프론트엔드 확인 필요)

주소, 필드 이름, 상태 코드는 같게 맞췄습니다. 아래만 다릅니다.

1. **길이 제한이 생겼습니다.** 이름 100자, 닉네임 50자, 아이 이름 100자, 성별 20자, 약관 JSON 4,000자,
   비밀번호 72바이트. 넘으면 400입니다.
2. **요청 본문은 64KB까지입니다.** 넘으면 413(`VALIDATION_ERROR`)입니다. 파일 업로드는 별도입니다.
3. **토큰이 없는 요청이 없는 주소로 가면 401입니다.** Django는 404였습니다. 로그인한 요청은 그대로 404입니다.
4. **Refresh 토큰은 JWT가 아니라 임의 문자열입니다.** 프론트는 그대로 저장했다가 보내면 됩니다.
5. **비밀번호 재설정 토큰의 모양이 다릅니다.** 메일의 링크 형식(`…#reset_token=…`)은 같습니다.
6. **비밀번호가 거절되면 이유를 알려 줍니다.** 가입은 `details.password`, 변경·재설정은 `details.new_password`에
   문구가 들어옵니다(예: "너무 흔한 비밀번호입니다."). Django는 필드 이름조차 주지 않았습니다.
7. **로그아웃은 실패하지 않습니다.** 만료됐거나 모르는 토큰을 보내도 200입니다. Django는 400이었습니다.
8. **로그인 시도 제한은 "IP + 이메일" 단위입니다.** 남이 다른 곳에서 틀린 비밀번호를 넣어도 본인의 로그인은
   막히지 않습니다. 대신 여러 IP에서 한 계정을 두드리는 것은 계정 단위로 막지 않습니다.
9. **토큰 갱신과 로그아웃에는 IP 제한이 없습니다.** 한 주소(통신사, 어린이집 와이파이)를 여러 사용자가 함께 쓰기
   때문입니다. 유효한 토큰 없이는 아무 일도 일어나지 않습니다.
10. **표지 주소에 `?v=숫자`가 붙고, 표지는 브라우저가 하루 동안 보관합니다.** 파일이 바뀌면 숫자가 바뀝니다.
    PDF는 보관되지 않습니다.
11. **모든 응답에 `X-Request-Id` 헤더가 있습니다.** 오류 본문의 `request_id`와 같은 값입니다.
12. **가입 때 필수 약관을 검사할 수 있습니다**(`REQUIRED_AGREEMENTS`). 빠지면 `details.agreements`와 함께 400입니다.
13. **아이 수에는 상한이 없습니다.** 팀 결정입니다.

## 결제가 붙으면서 달라지는 점 (팀 확인 필요)

1. **활동지에 가격이 생깁니다.** 0원이면 지금처럼 누구나 PDF를 받습니다. 0원보다 크면 구매자만 받습니다.
2. **유료 활동지의 `pdf` 주소는 그냥 열면 404입니다.** 구매자는 `POST /activities/{id}/download`(API 40)를 불러
   5분짜리 `download_url`을 받아 엽니다. 표지(`image`)는 계속 공개입니다.
3. **영구 소장한 활동지는 장바구니에 담을 수 없습니다**(409 `ALREADY_PURCHASED`). 팀이 정했던 "무료 장바구니" 규칙을
   명세 0절의 원래 규칙으로 되돌린 것입니다. 7일 이용권으로 보고 있는 활동지는 영구 소장으로 사기 위해 담을 수 있습니다.
4. **주문 생성 응답의 `payment_session_token`이 결제사 주문 번호입니다.** 프론트는 이 값을 결제창의 `orderId`로
   쓰고, 승인 요청의 `pg_order_id`로 다시 보냅니다. 0원 주문은 이 값이 `null`이고 바로 `paid`가 됩니다.
5. **한 사용자의 한 활동지는 한 번에 한 주문만 결제로 갑니다.** 새 주문을 만들면 아직 결제를 시작하지 않은 이전
   주문은 취소됩니다. 결제 확인이 진행 중인 주문과 **같은 활동지가 들어 있으면** 새 주문은 409입니다. 다른 활동지는 주문할 수 있습니다.
6. **승인 응답이 503이면 "확인 중"입니다.** 실패가 아닙니다. 프론트는 같은 승인 요청을 다시 보내도 되고(두 번
   결제되지 않습니다), 주문 상세를 다시 조회해도 됩니다. 서버도 1분마다 결제사에 다시 묻고, 승인 요청이 결제사에
   닿지 않았던 것이면 다시 보냅니다.
7. **주문 상태에 `review`가 있습니다.** 결제 금액이 주문 금액과 다를 때이며, 권한을 주지 않고 사람의 확인을 기다립니다.
8. **결제 내역(API 51)의 응답은 `{count, results}`입니다.** 명세의 표는 주문 생성(48)의 복사본이라 목록 형태를 정했습니다.
9. **웹훅(API 50)은 토스페이먼츠가 보내는 모양을 받습니다**(`eventType`, `createdAt`, `data`). 명세의 필드와 다릅니다.
10. **환불은 구매자가 요청하고 관리자가 사유를 보고 수락합니다**(팀 결정). 구매자는 결제된 주문에
    `POST /orders/{id}/cancel` `{reason}`(API 54)을 보냅니다. 돈도 권한도 움직이지 않고 요청만 남으며, 응답은
    `{order_id, status:"paid", refund_amount:0, refund_request:"requested"}`입니다. 주문 한 건에 열린 요청은 하나입니다.
    주문 상세의 `refund_request`에 `{status, reason, admin_note}`가 나옵니다(`requested`/`approved`/`rejected`, 없으면 `null`).
    거절되면 다시 요청할 수 있습니다. 환불은 주문 전체 단위이며, 부분 환불은 결제사 화면에서 사람이 처리합니다.
    결제 전 주문은 지금처럼 바로 취소됩니다(`refund_request:null`).
11. **저장 카드(API 55~58)는 없습니다.** `payment_method_id`에 값을 보내면 400입니다.
12. **구매했지만 비공개가 된 활동지**는 구매 목록에 남고 PDF도 받을 수 있지만, 표지 주소는 404입니다.
13. **유료 주문은 환불 고지에 동의해야 만들어집니다.** 예상 금액 응답(API 47)의 `refund_notice`가 결제 버튼 옆에
    보여 줄 문구이고, 주문 생성(API 48)에 `agreed_to_refund_notice: true`가 없으면 400입니다. 동의한 시각은 주문에
    남습니다. 0원 주문에는 필요 없습니다. **문구는 `OrderService.REFUND_NOTICE`에 있으며 팀(가능하면 법률) 확인이 필요합니다.**
14. **7일 이용권과 영구 소장을 다른 가격으로 팝니다.** 활동지의 `price`가 영구 소장가, `rental_price`가 7일 이용권
    가격(`null`이면 7일 이용권을 팔지 않음), `rental_days`는 7입니다. 7일 이용권은 0원보다 크고 영구 소장가보다 낮아야 합니다.
    주문·예상 금액 요청에서 7일로 살 활동지를 `rental_activity_ids`(`activity_ids`의 일부)에 넣습니다. 빼면 전부 영구 소장입니다.
    - 7일은 **결제가 확정된 순간부터** 셉니다.
    - 영구 소장 중이면 다시 살 수 없고, 7일 이용 중이면 7일 이용권은 다시 살 수 없지만 영구 소장으로는 살 수 있습니다.
      기간이 끝나면 둘 다 살 수 있습니다(409 `ALREADY_PURCHASED`가 그 외의 경우).
    - 기간이 끝나면 다운로드 링크 발급은 403 `ACCESS_EXPIRED`입니다.
    - 구매 목록(API 39)의 각 항목에 `plan`(`permanent`/`rental`), `expires_at`, `expired`가 붙고, 끝난 이용권도 목록에 남습니다.
    - **이미 내려받은 파일은 사용자 기기에 남습니다.** 서버가 막는 것은 7일 뒤의 다시 받기입니다.
15. **PDF가 구매자 링크로 나갈 때마다 기록이 남습니다**(누가, 어떤 활동지를, 언제). 기록이 써지지 않으면 파일도 나가지
    않습니다. 2026-11-25부터 **파일을 받아 간 인터넷 주소(IP)와 브라우저 정보(User-Agent, 255자까지)도 함께 저장합니다**
    (`pdf_downloads.ip_address`, `user_agent`). 링크가 남에게 넘어가 받아진 것과 구매자 본인이 받은 것을 가려내기 위한
    것이고, 개인정보처리방침의 수집 항목에 적어야 합니다. 환불 요청과 관리자의 주문 상세에는 지금처럼 횟수와 처음·마지막
    시각만 나오고, 주소와 브라우저 정보는 DB에서 직접 봐야 합니다(API로는 내보내지 않음).
16. **다운로드 권한은 링크를 만들 때와 파일을 내보낼 때 두 번 확인합니다.** 5분짜리 링크를 받아 둔 뒤라도 기간 만료,
    환불, 계정 정지가 일어나면 그 링크는 404입니다.
17. **환불 요청이 걸려 있는 동안에는 그 주문의 PDF를 받을 수 없습니다**(링크 발급 409). 관리자가 본 다운로드 기록이
    결정할 때까지 바뀌지 않게 하려는 것입니다. 거절되면 다시 받을 수 있습니다.
18. **한 활동지의 다운로드 링크 발급은 계정당 1시간에 10번까지입니다**(넘으면 429).

19. **활동지를 등록할 때 `price`는 반드시 적습니다**(무료는 `0`). 빠뜨리면 400입니다. 전에는 빠뜨리면 0원이 되었고,
    0원이고 공개된 활동지의 PDF는 누구나 받을 수 있어서 입력 실수 하나로 유료 자료가 열릴 수 있었습니다.
20. **결제 승인(API 49)은 한 계정이 10분에 20번까지입니다**(넘으면 429). 한 번 부를 때마다 결제사를 최대 30초 기다리기 때문입니다.
21. **웹훅은 한 주문에 대해 1분에 6번까지만 결제사에 조회합니다.** 넘으면 조회하지 않고 503으로 답해서, 결제사가 진짜
    알림을 나중에 다시 보내게 합니다. 주문 번호를 아는 사람이 웹훅을 반복 호출해 서버와 결제사 한도를 소모시키는 것을
    막는 것이고, 우리가 만든 적 없는 주문 번호와 결제 시도 없이 닫힌 주문은 조회 없이 200입니다. 같은 이유로
    **주문 생성은 한 계정이 10분에 30번까지**입니다(넘으면 429). 남는 한계: 구매자가 자기 주문 번호로 웹훅을 계속
    두드리면 그 주문의 진짜 알림(결제사 화면에서 한 환불)이 그동안 503을 받습니다. 그때 `webhook_capped` 로그가
    남고, 관리자의 재조회(`POST /admin/orders/{id}/reconcile`)에는 이 제한이 없습니다.
22. **결제사가 "너무 자주 물었다"(429)나 "시간 초과"(408)로 답하면 결제 실패로 보지 않습니다**(확인 중으로 둠). 전에는
    실패로 읽어서, 승인이 진행 중인 주문이 닫히고 뒤이어 온 승인 성공이 버려질 수 있었습니다. 이미 닫힌 주문에 승인
    성공이 오면 `payment_done_for_closed_order` 로그가 남습니다(돈은 나갔는데 권한이 없는 경우이므로 사람이 환불).

16~18은 다운로드 규칙을 더 엄격하게 해 달라는 요청을 서버가 해석해 넣은 것입니다. 17은 `Activities.downloadState`의 `refund`
분기, 18은 `OrderController.LINKS_PER_SHEET_PER_HOUR`에서 풀거나 바꿀 수 있습니다.

## 소셜 로그인 (카카오·네이버·구글, 2026-11-25)

`POST /api/v1/auth/social/{provider}` (`kakao` | `naver` | `google`). 프론트가 사용자를 공급자 로그인 화면으로 보내고,
돌아온 **인가 코드**를 그대로 서버에 넘깁니다. 서버가 그 코드를 공급자 토큰으로 바꾸고 프로필을 읽어 우리 토큰을 줍니다.
요청·응답 형식은 [docs/API_SPEC.md](docs/API_SPEC.md) 3.10에 있습니다. 명세 v1.5(08번)의 Apple은 만들지 않았고 구글을 넣었습니다.

- **켜는 법**: 공급자마다 키 두 개를 서버 환경 변수에 넣고 재시작합니다. 키가 없는 공급자의 주소는 404입니다.
  `KAKAO_CLIENT_ID`(REST API 키)·`KAKAO_CLIENT_SECRET`, `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET`,
  `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET`. 카카오만 시크릿 없이도 켜집니다(카카오 콘솔에서 시크릿을 꺼 둔 경우).
  각 공급자 콘솔에 **프론트의 Redirect URI**를 등록해야 하고, 이메일 제공 동의 항목을 켜야 합니다(카카오는 비즈 앱이나
  테스트 앱이어야 이메일 항목을 쓸 수 있다고 문서에 적혀 있습니다).
- **계정은 공급자가 준 회원 번호로 묶입니다.** 이메일은 처음 한 번, 계정을 찾거나 만들 때만 씁니다. 그 뒤 공급자 쪽
  이메일이 바뀌어도 같은 계정입니다.
- **이메일을 공급자가 보증할 때만 기존 계정에 연결합니다.** 보증으로 보는 경우: 카카오의 `is_email_valid`와
  `is_email_verified`가 모두 true, 구글의 `email_verified`가 true이면서 주소가 `@gmail.com`이거나 `hd`(구글이 운영하는
  도메인)가 있는 경우. **네이버는 프로필에 인증 여부가 없고 사용자가 연락처 이메일을 아무 주소로나 바꿀 수 있어서
  보증으로 보지 않습니다.**
- **보증되지 않은 이메일**: 그 이메일의 계정이 이미 있으면 409 `ALREADY_EXISTS`(이메일·비밀번호로 로그인하라고 안내).
  없으면 새 계정을 만듭니다. 이때 남의 이메일을 연락처로 적어 둔 사람이 그 주소의 계정을 먼저 만들 수 있는데, 진짜
  주인이 **비밀번호 재설정**을 하면 모든 세션이 끊기고 그 소셜 연결도 지워져서 계정이 주인에게 넘어옵니다(주인은
  가입 화면에서 "이미 가입한 이메일"을 보게 되므로 재설정으로 안내해야 합니다). 그래서 네이버로 가입한 사람이 비밀번호를
  재설정하면 그 뒤로는 네이버 로그인이 409가 되고 이메일·비밀번호로 로그인해야 합니다. 주인이 **이메일을 보증하는
  공급자(카카오, 구글)로 로그인해도 똑같이** 보증 없는 연결과 그때까지의 모든 세션이 지워집니다.
  남는 한계: 먼저 만든 사람이 넣어 둔 것(아이 정보, 이름·닉네임, 장바구니, 약관 동의 기록)은 계정에 그대로 있습니다.
- **보증 없는 소셜 연결이 남아 있는 계정은 관리자가 되지 않습니다.** 그런 계정의 이메일을 나중에 `ADMIN_EMAILS`에
  넣어도, 비밀번호를 재설정해 그 연결이 지워지기 전까지는 관리자 API가 403입니다.
- **이메일이 안 오면 가입되지 않습니다**(409 `EMAIL_REQUIRED`). 사용자가 이메일 제공에 동의하지 않았거나 카카오가 만료된
  주소를 준 경우입니다.
- **관리자 이메일은 소셜 로그인이 안 됩니다**(403). 관리자는 이메일로 정해지므로, 공급자가 말해 준 이메일이 관리자
  권한으로 들어가는 두 번째 문이 되지 않게 했습니다.
- **필수 약관**: 새 계정이 만들어지는 첫 로그인에만 `agreements`가 필요합니다(이메일 가입과 같은 `REQUIRED_AGREEMENTS`).
  없으면 409 `AGREEMENTS_REQUIRED`이고, **인가 코드는 한 번만 쓸 수 있어서 이 경우 공급자 로그인부터 다시** 해야 합니다.
  프론트는 소셜 버튼을 누르기 전에 약관 동의를 받아 두고 항상 `agreements`를 함께 보내는 편이 안전합니다.
- **소셜로 만든 계정에는 아무도 모르는 비밀번호가 들어갑니다.** 이메일·비밀번호 로그인은 안 되고, 비밀번호 재설정을
  하면 그때부터 됩니다. 비밀번호 변경(현재 비밀번호 필요)은 재설정 전에는 쓸 수 없습니다.
- **횟수 제한**: 같은 IP에서 10분에 30번(다른 인증 API와 같은 `AUTH_IP_LIMIT`).
- **개발 서버**: 2026-11-25에 이 코드와 `V2` 스키마가 올라가 있습니다. 세 공급자의 키가 모두 비어 있어 지금은 세 주소가
  모두 404입니다. 키를 `/etc/yippee/env`에 넣고 `sudo systemctl restart yippee` 하면 켜집니다.
- **확인하지 못한 것**: 세 공급자 모두 **실제 서버에 붙여 보지 못했습니다**(앱 등록과 키가 있어야 함). 주소·필드 이름·
  인증 플래그는 2026-11-25에 각 공급자의 공식 문서에서 읽은 것이고, 테스트는 공급자를 흉내 낸 로컬 서버로 돌렸습니다.
  문서에 없어서 가정한 것: 카카오·구글이 잘못된 코드에 주는 HTTP 상태(무엇이 오든 토큰이 없으면 400으로 답하게 함),
  네이버가 오류를 200 안에 담아 주는지(양쪽 다 처리), 구글 userinfo가 `hd`를 주는지(안 주면 gmail.com이 아닌 구글
  계정은 "보증되지 않은 이메일"로 처리됨). 구글의 팝업 방식(`initCodeClient`)은 문서상 Redirect URI가 "호출한 페이지의
  origin"이므로 프론트가 그 값을 `redirect_uri`로 보내야 합니다.

## 아직 확인되지 않은 것

이 저장소의 테스트는 H2로만 실행해 봤습니다. 아래는 코드로 대비했지만 실제로 돌려 보지 못했습니다.

- **소셜 로그인**: 실제 카카오·네이버·구글과는 붙여 보지 못했습니다(위 "소셜 로그인"의 마지막 항목).

- **실제 MySQL**: 2026-11-24에 개발 서버의 MySQL 8.0.46에서 스키마 생성과 전체 테스트(81개 중 80개 통과, 실연결 시험 1개는
  키가 없어 건너뜀)를 서울 시간대 JVM으로 돌려 확인했습니다. 2026-11-25에 `V2` 스키마와 98개(97개 통과, 같은 1개 건너뜀)를
  같은 MySQL의 테스트용 DB에서 다시 확인했습니다. 이 PC에서 SSH 터널로 붙여 돌렸고, 서버의 `max_connections`가 60이라
  한 번에 다 돌리면 네 번째 테스트 묶음이 연결을 못 얻습니다(소셜 로그인 11개는 따로 돌림). 터널로는 전체가 40분쯤 걸립니다. CI는 MySQL 8.4를 대상으로 하는데, 그 버전에서는 아직
  돌려 보지 못했습니다. 동시 요청이 실제로 몰릴 때의 잠금 동작은 테스트가 다루는 범위까지만 확인된 것입니다.
- **실제 토스페이먼츠**: 2026-11-24에 테스트 키로 실제 테스트 서버에 붙여, 키가 받아들여지는 것과 "없는 결제"·"틀린 키"
  응답이 가정대로 읽히는 것까지 확인했습니다(조회·승인·취소 각 1회, 돈은 움직이지 않음). **실제로 승인되는 결제,
  승인된 결제의 환불, 웹훅은 아직 돌려 보지 못했습니다.** 그건 프론트 결제창(클라이언트 키)과 떠 있는 서버가 있어야 합니다.
  같은 확인을 다시 하려면 `TOSS_SECRET_KEY`에 `test_sk_…` 키를 넣고 `./gradlew test --tests "*TossGatewayTest*"`를
  실행합니다. 키가 없거나 운영 키(`live_sk_…`)이면 그 시험은 건너뜁니다.
- **Docker 빌드와 EC2에서의 부하.**
- **비밀번호 재설정 메일.** 가입 인증 메일은 2026-11-25에 개발 서버에서 도착까지 확인됐습니다(프론트에서 한 첫 가입:
  인증 → 가입 → 내 정보 → 아이 등록이 모두 성공). 재설정 메일은 `PASSWORD_RESET_FRONTEND_URL`이 비어 있어 아직 500입니다.
  인증번호 발송 요청은 한 번에 5.3초 걸렸습니다(두 번 모두). 메일을 요청 안에서 보내기 때문인데, 서버에서 재 보니 Gmail
  접속·로그인이 약 2.2초이고 서버의 자기 이름 조회는 0.01초였습니다. 나머지 약 3초가 어디서 쓰이는지는 재지 않았습니다.

**실결제는 앞의 두 가지가 통과하기 전에는 열지 않습니다.**

## Django 서버에서 넘어오지 않은 것

- **데이터는 옮겨지지 않습니다.** 카테고리, 등록돼 있던 활동지 4개와 그 파일, 계정은 새로 넣어야 합니다.
  활동지는 관리자 API로 다시 등록합니다.
- **메일은 SMTP로만 보냅니다.** Django main의 마지막 커밋은 Resend를 HTTP 방식으로 붙였습니다. Resend를 계속
  쓰려면 Resend의 SMTP 접속 정보를 `EMAIL_*`에 넣어야 합니다(제공 여부와 값은 Resend 문서에서 확인 필요).
- **빠진 것**: 활동 기록 테이블(아이 삭제 시 함께 삭제되던 자리), 등록된 활동지의 파일 교체, 관리자용 사용자 화면.
- **결제 수단은 카드·간편결제를 가정합니다.** 무통장 입금은 입금 전까지 주문이 "확인 중"으로 남아 그 사용자의
  다음 주문을 막습니다.

## 아직 고치지 않은 것과 그 이유

- **파일 저장소**: 서버 디스크에 저장합니다. S3·R2로 갈지는 EC2 인프라를 구성할 때 정합니다(위 "EC2에 올릴 때"의 세 조건).
- **회원 탈퇴(명세 15번)**: 만들지 않았습니다. 주문·환불 요청·다운로드 기록이 사용자 번호를 붙들고 있어서 행을 지우는
  방식은 안 되고, 개인정보(이메일·이름·연락처·아이 정보)를 지우거나 알아볼 수 없게 바꾸고 거래 기록은 정해진 기간
  남기는 방식이어야 합니다. 보관 기간은 팀이 개인정보처리방침에 정해야 합니다.
- **미리보기(명세 38번)**: 없습니다. 전자상거래법 제17조 제6항은 디지털콘텐츠의 청약철회를 막으려면 "불가능하다는
  사실의 표시"와 함께 시험 사용 상품 제공 등의 조치를 요구합니다(위키문헌 전사본으로 읽음, 시행령 세부는 미확인).
  고지 문구와 동의만으로는 부족할 수 있으므로 상세 페이지에 샘플 쪽을 보여 주는 기능이 필요합니다.
- **묶음 주문의 부분 환불**: 같은 조 제2항 제5호 단서는 나눌 수 있는 콘텐츠에서 제공이 시작되지 않은 부분은
  철회할 수 있다고 합니다. 여러 활동지를 한 주문으로 사면 내려받지 않은 활동지가 여기에 해당할 수 있는데, 서버의
  환불은 주문 전체 단위입니다. 그런 건은 결제사 화면에서 부분 환불해야 하며 그 경우 권한은 자동으로 회수되지 않습니다.
- **영구 소장으로 올려 산 주문의 환불**: 7일 이용 중에 영구 소장을 산 뒤 그 주문을 환불하면 남아 있던 이용 기간도
  함께 끝납니다(권한 행이 주문 하나만 기억함. `OrderService.grant`에 표시).
- **7일 이용권의 "7일"은 코드 상수입니다**(`Activities.RENTAL_DAYS`). 활동지마다 기간을 달리하는 기능은 없습니다.
- **Refresh 토큰 수명**: 24시간이라 하루에 한 번 다시 로그인해야 합니다. `JWT_REFRESH_TTL_SECONDS` 값 하나로
  바꿀 수 있고, 얼마로 할지는 팀이 정합니다. 토큰 회전은 넣지 않았습니다.
- **IP당 한도**: 로그인·가입·인증번호 발송은 같은 IP에서 10분에 30번입니다(`AUTH_IP_LIMIT`). 여러 가정이 한 주소를
  쓰는 곳에서는 낮을 수 있어 운영하면서 조정합니다.
- **이메일당 한도**: 인증번호 발송과 재설정 메일은 이메일 하나에 10분 10번입니다. 남이 그 한도를 써 버릴 수 있지만,
  받은편지함이 메일로 뒤덮이는 것을 막는 쪽을 택했습니다.
- **무통장 입금**, **부분 환불 자동 처리**, **관리자 화면(웹 페이지)**: 없습니다. 관리자 기능은 API뿐입니다.

## 사람이 직접 해야 하는 일

- 금액이 맞지 않는 결제(`review`)는 관리자 API의 주문 목록(`?status=review`)에서 찾아 환불합니다. 부분 환불은
  결제사 화면에서 처리합니다. 로그의 `payment_amount_mismatch`, `payment_needs_review`, `duplicate_entitlement`,
  `payment_done_for_closed_order`는 바로 확인해야 하는 경보입니다. `unhandled`는 서버 오류입니다.
- **환불 요청**은 관리자 API의 `orders/refund-requests?status=requested`에서 보고 수락하거나 거절합니다. 알림은 없으므로
  주기적으로 확인해야 합니다. 내려받지 않았고 결제 후 7일 이내인 요청은 법이 보장하는 철회에 해당할 수 있으니
  다운로드 기록(`download_count`)과 결제 시각을 보고 판단합니다. 수락이 503으로 끝나면 결제사 확인이 늦는 것이고,
  요청은 그대로 남아 있다가 결제사가 환불을 알려 오면 닫힙니다.
- 약관 동의 항목, 환불 고지 문구, 탈퇴 시 보관 기간, 토큰 수명은 팀이 정해야 합니다.

`src/main/resources/common-passwords.txt.gz`는 Django(`django.contrib.auth`, BSD 라이선스)의 흔한 비밀번호 목록입니다.
